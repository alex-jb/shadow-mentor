# Shadow：把验收要求和执行证据对齐

2026-11-11，纽约。研究问题是：工具说“通过”时，消费者能不能确认这次运行真的满足了预先约定的条件？

## 从需求澄清走到可复核的验收

[Oracle 的 FDE 论文](https://arxiv.org/html/2611.03551v1)有很直接的启发。它以**一个**真实企业 Text-to-SQL 项目为参考，用模拟客户考察发现要求及后续交付。汇总中，4,122 个在对话中披露的事实实例里有 874 个没有进入回读前提交的需求；八个表 2 交付运行中，只有两个同时满足准确率、生产查询编译失败数和延迟要求。另一次单独的 harness 对照不在八个运行内。不能据此估计一般 Agent 的成功率。

Oracle 已有模拟客户回读、未决事项、来源追踪和分离式工作流中的计划冻结。本项目不声称发明这些步骤。[Ambig-SWE](https://arxiv.org/html/2502.13069v3)已分开评估缺失需求的识别、提问和补丁成功；[TiCoder](https://www.microsoft.com/en-us/research/publication/llm-based-test-driven-interactive-code-generation-user-study-and-empirical-evaluation/)让用户通过测试部分明确意图；[τ-bench](https://arxiv.org/html/2406.12045v1)的作者也明确讨论了终态正确但缺少必要确认的问题。Shadow 的范围是**调用者已经声明条件以后**，区分本次有效观测、错范围或错运行的记录，以及缺失的证据。

## 本轮已经执行

实现了[研究原型](../../research/acceptance-contract-20261111/README.md)：先固定验收计划，再用运行 ID、计划摘要、环境范围和逐项观测作判定。确有观测且不符才拒绝；缺观测或要求未定则暂缓。不同传输方式可按计划将某项排除，但不能把“没有适用检查”当通过。

把旧 recorder 的**七条存档 fixture**组成 **16 个事后编写的离线条件**。不增加原生执行或历史缺陷；新计划是在回放判定前冻结，不是回溯证明旧运行当时已绑定计划。

| 读取的信息 | 与人工构造预期一致 | 不支持的接受 | 不支持的拒绝 |
| --- | ---: | ---: | ---: |
| 只读原生汇总 | 5/16 | 10 | 1 |
| 读取条件和观察，但不校验运行 ID／计划摘要 | 14/16 | 2 | 0 |
| 同信息普通脚本 | 16/16 | 0 | 0 |
| 研究原型 | 16/16 | 0 | 0 |

最重要的反例是：旧工具报告完全相同，实际可以是返回 200、合法跳过或返回 500。只看该报告，无法在这些条件下同时保留有效通过并排除不支持的接受。状态 500 是否失败仍由消费者定义；不是所有 500 都是产品缺陷。合法 stdio 排除且 RPC 匹配的对照通过，空范围则暂缓。

同信息普通脚本与原型完全一致。差异来自可见的检查条件、观察和绑定，而非新的推理算法。14 项单元测试通过，独立代码审查的回放结果与保存结果字节一致；代码代理复核不算独立人类标注或留出。既往仍只有**两个工具族的三个已公开修复缺陷**；第三工具族是适用性对照。

## 真实本地执行：同一个数字可以来自不同账户

另做了[SQLite 对照](../../research/acceptance-contract-20261111/sqlite-results.json)。对三个虚构账户，先冻结每次运行的要求，再启动本地子进程执行固定查询。**7 次查询尝试，另有 2 次运行后的证据替换**；没有外部数据库、真实客户或模型。

| 对照 | 实际观察 | 验收 |
| --- | --- | --- |
| 要求已付费且未取消的账户数为 1；运行限定查询 | SQL 完成，结果 1 | 通过 |
| 同一计数要求；运行全表计数 | SQL 完成，结果 3 | 拒绝；若明确要求全表账户数 3，另一次运行通过 |
| 改选已付费但已取消账户，仍只核对数量 | SQL 完成，结果也是 1 | 数量检查通过；不能据此确认选对账户 |
| 冻结要求为有序账户 ID `[1]`，分别查询两个子集 | 实际 `[1]` 与 `[2]` | 前者通过、后者拒绝 |
| 缺失字段的固定 SQL；或运行后换用旧计划记录、移除观测 | 未取得可采纳的计数证据 | 暂缓 |

这提供了一个关键的**负面结果**：即使证据来自指定运行、数量也完全正确，错误子集仍可以通过只检查数量的计划。增加正确的业务判定需要要求本身覆盖账户身份，并采集能证明它的观测；工具不能从正确数字推断正确人群。此结论只适用于构造的本地案例，不证明通用 SQL 正确性。
