1 · What Shadow is (and is not)

Shadow turns an AI/ML credit or compliance decision into a signed, tamper-evident, reason-code-mapped evidence bundle that a third party can verify offline — independently of the model vendor. It is the non-conflicted verifier an examiner needs; it is not the model, and it does not make or change the lending decision. The verdict layer is deterministic rules; the LLM personas write human-readable rationale only.

2 · Cryptographic model

PropertyMechanism
Authenticity + non-repudiationEd25519 asymmetric signatures (RFC 8032). Only the private-key holder can sign; anyone with the public key can verify — so a bank verifies without being able to forge, and the vendor cannot silently swap the record. Ed25519 is the default whenever a signing key is configured.
Integrity + orderingSHA-256 hash-chain: each event binds the hash of the prior event (previous_hash) + its own payload hash. Editing, reordering, inserting, or truncating any event breaks a downstream link.
Independent verificationA single self-contained offline WebCrypto verifier (verify.html) — no network, no dependencies, CSP-safe — re-checks every link + the signature against the public key. A CLI (bin/shadow-verify.mjs) and MCP tool do the same; run it in your own CI/SIEM.
CanonicalizationJSON canonicalization (sorted keys) so signatures are stable across environments; semantic tamper (e.g. 1 vs "1") is caught, byte-parity verified Node ↔ browser.
What a green ✓ proves — precisely. It proves integrity: this is the record that was sealed, unaltered. It does not assert content authenticity — that the agent's behaviour at capture time was benign, injection-free, or correct. Shadow states this boundary everywhere; it does not sell a clean bill of health it cannot give.

3 · Tamper coverage (adversarially tested)

AttackResult
Edit an event after seal✓ caught — payload hash mismatch
Reorder / insert an event✓ caught — prev_hash mismatch at the exact seq
Truncate the chain✓ caught — seq/link discontinuity
Re-sign with a different key✓ caught — signature fails against the pinned public key

Each is a failing assertion in the test suite (edit/reorder/insert/truncate/wrong-key). Full attack table: docs/THREAT_MODEL.md (seven classes).

4 · Data handling & deployment

  • Local-first. Verification runs on-device / in-browser; no evidence is uploaded to a Shadow-controlled host. It runs fully offline (pull the network cable).
  • Zero telemetry. Neither the library nor the CLI verifiers open an outbound socket to a Shadow host — verifiable by grepping the source.
  • Self-host. MIT core; run the verifier inside your own perimeter — evidence never leaves the bank's boundary.
  • The public demo uses synthetic data only. Production pilots run on your data, under NDA, in your environment.

5 · Regulatory mapping (the depth, not just the crypto)

  • Reg B / ECOA — adverse-action reason codes (AA01–AA06) mapped per decision; a signed reason-code dictionary bound into the attestation (dictionary_hash) so a post-hoc swap breaks verification.
  • GDPR Article 22 + Schufa (C-634/21) / Dun & Bradstreet (C-203/22) — automated-decision explainability, enforceable in the EU today.
  • ECOA §701 protected-class proxy detection; disparity metrics (AIR / SMD, 4/5 rule).
  • Each triple is documented in docs/CITATION_MAP.md.

6 · Honest status & roadmap

Pre-1.0. Not yet independently audited. No production certification, no enterprise RBAC/SSO, no cloud isolation as shipped. The cryptographic core is sound and adversarially tested; deployment hardening (authn/rate-limit on paid endpoints, size caps) is in progress. SOC 2 is a planned fast-follow, initiated on a design partner's first security questionnaire. We label capabilities on an explicit ladder (source-authored → host-tested → device-validated) and never over-claim.
