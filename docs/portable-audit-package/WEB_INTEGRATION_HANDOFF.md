# Web integration handoff (future increment — NO Web changes were made)

This increment delivers the exact prerequisite the Web repo needs to build
package import: a deterministic, committed-contract package producer and an
independent reference verifier.

## What the Web increment can now rely on

- **Contract**: `shadow-portable-audit-package/1.0` as specified in
  `PORTABLE_AUDIT_PACKAGE_CONTRACT.md` (layout, signed fields, closed role +
  failure vocabularies, two-way completeness, derived-view boundary).
- **Reference producer**: `bin/shadow-audit-package.mjs create --fixture
  banking` — byte-deterministic, so the Web repo can pin golden fixtures.
- **Reference verifier semantics**: `verifyPackageDir` in
  `lib/portable-audit-package.mjs` — the browser implementation must
  reproduce its check sequence and failure classes in WebCrypto
  (`verify.html` in this repo is the WebCrypto Ed25519 precedent).
- **Presentation member unchanged**: `presentation/shadow-flow-export.json`
  feeds the existing, unchanged Web flow-import pipeline
  (size gate → parse → validateFlowExport → adapt → validateWebAuditCase).
  This is regression-pinned by the parity test against
  `bin/shadow-flow-export.mjs`.

## Display states the Web must implement (from PACKAGE_WEB_CONSUMPTION.md)

`TAMPERED · INCOMPLETE · UNEXPECTED_MEMBER · UNSUPPORTED · UNVERIFIABLE ·
VERIFIED_FIXTURE_KEY · VERIFIER_DISAGREEMENT` — all now correspond 1:1 to
producer-side failure classes or verdicts, so browser fixtures can be
generated by mutating a golden package exactly as
`test/shadow-audit-package-verify.test.js` does.

## Open product decisions carried forward

1. Delivery form for the browser: directory-of-files vs single-envelope JSON
   (the CLI writes a directory; an envelope adapter would be new, separate
   work).
2. Whether the browser re-verifies the evidence bundle chain in WebCrypto in
   the first Web increment or displays "bundle not re-verified in browser"
   until that lands.
3. Persistence stays OFF by default; if it ever lands: safe metadata only
   (package_id, case_id, schema versions, verdict, fingerprint) — never
   member bytes, payload contents, identity_ref, reviewer identities.

## Rules restated for the Web increment

- The browser never signs, never holds private keys, never mutates a signed
  member; review/approval actions produce Core-side NEW packages with
  `supersedes` references (supersession is not yet implemented Core-side).
- The shipped `verification/verification-result.json` renders only alongside
  the browser's own independent outcome; disagreement is a first-class state.
- Web import success proves neither Flow vendor import nor native Lens
  behavior; `FORBIDDEN_PHYSICAL_CLAIMS` hard-error stays.
- Cross-surface parity: browser outcomes for the golden + mutated fixtures
  must match this CLI's outcomes (Node/Python parity precedent).
