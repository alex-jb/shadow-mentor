# Independent evaluation plan (proposal)

This is a planning document, not a preregistration or a completed evaluation. The historical repairs, recorder archive, and SQLite controls above were developed with their outcomes known. Exclude those sources and their near duplicates from any new blind evaluation.

**Question.** When a team fixes its acceptance obligations before execution, which errors are attributable to a weak criterion, missing observations, or the interpretation rule? Separately measure how long it takes to normalize a new tool's observations. A tie with a short script is an informative result.

**Unit and selection.** Use a distinct requirement and controlled run as a unit, and keep all evidence substitutions grouped with their originating run. Select at least two unrelated local testing workflows before collecting outcomes. Include ordinary successes, admissible mismatches, infrastructure errors, and deliberately inapplicable checks. Choose workflows by documented coverage gaps and reproducibility, not by whether Shadow detects a discrepancy. Do not collect customer or credential data.

**Separation.** A reviewer who has not seen implementation outputs writes the acceptance criteria and applicability matrix. Freeze them and the scoring rules before the new runs. A separate reviewer checks raw observed outputs against the frozen criteria, without seeing evaluator verdicts. Mark disputed or unjudgeable examples separately and retain the reasons. Human reviewers, labels and resulting runs are not yet available.

**Matched information.** Save a native output-only analysis as an information ablation. For the primary comparison, give both a plain script and the prototype the same typed plan, observation fields, documented exclusions and budget for adapter implementation. Do not give the prototype a richer observation channel while calling a difference method performance. Keep evidence-collection failures distinct from semantic mismatches.

**Measures.** Report unsupported acceptances, unsupported rejections, expected passes withheld, and run groups in each denominator. Record adapter implementation and reviewer time, scope contradictions and incomplete requirements. Report results by workflow and observation type; do not pool controlled SQL, stubbed checker logic, and real tool execution into one success rate.

**Interpretation.** If the ordinary script ties and takes no more effort, report the result as an integration lesson rather than a better algorithm. If both miss a counterexample because the criterion is underspecified, revise the requirement and rerun as development only; do not reclassify it as a held-out success. A new evaluation version needs new untouched runs.
